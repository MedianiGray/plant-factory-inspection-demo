# 方案设计与技术取舍

## 1. 问题定义

实训室的固定监测已经把「看见」做到了：传感器阵列持续采集空气温湿度、光照 PAR、CO₂，营养液侧采集 EC、pH、溶解氧、液温；平台侧有阈值告警、场景联动、定时抓拍、设备日志。

但固定侧止步于「发现」，止步不到「确认」。三处缺口：

| 缺口 | 具体表现 | 依据 |
|---|---|---|
| 点位盲区 | 传感器按固定点位安装，多层架体之间、层内远端覆盖不到，数据是棚内均值 | 实训室传感器清单均为固定点位 |
| 确认盲区 | 阈值告警只给数值异常，误报与真实异常混在一起，仍需人到架位肉眼确认 | 平台阈值告警功能；现场 HMI 十路「运行/手动」、调光 50% 的观察 |
| 时间盲区 | 人工巡检次数有限，夜间与无人时段滞后；固定摄像头视角不可移动 | 现场巡检流程观察 |

因此方案命题不是「再加传感器」，而是**把告警的确认环节接起来**。

## 2. 协同关系

| 维度 | 固定侧 | 移动侧（myAGV） |
|---|---|---|
| 工作方式 | 7×24 连续采集 | 按任务出动，完成回停靠点 |
| 覆盖范围 | 固定点位，给场域均值 | 导航到任意架位，近距特写 |
| 承担任务 | 发现异常、阈值告警、留数据 | 现场复核、拍照识别、回传结果 |
| 局限 | 不能移动，告警后无法自己确认 | 单台车不能同时盯所有点位 |

结论：两者是分工，不是谁替代谁。一台移动车共享给全部固定点位，才是成本上可行的做法。

## 3. 六步闭环

1. **固定告警**：环境参数越限，平台按阈值触发告警。
2. **智能派单**：智能体把告警翻成结构化任务——点位 + 动作，不再停在通知页。
3. **导航出动**：NAV2 自主规划路径，驶向目标架位。
4. **到点拍照**：车载摄像头近距拍照，复用现有识别能力复核。
5. **记录生成**：大模型把复核结果写成结构化巡检记录草稿。
6. **人工确认**：人确认处置，调光、加肥、用药这类动作必须由人执行。

闭环的关键在第 6 步：机器只做到「建议」。

## 4. 分层架构

| 层 | 内容 | 归属 |
|---|---|---|
| 应用层 | 巡检看板、任务管理、记录确认界面 | 本方案 |
| 智能体层 | 任务派发（ReAct 任务链）、记录生成（大模型） | 本方案新增 |
| 平台层 | 物模型接入、场景联动、阈值告警、设备日志 | 实训室已有 |
| 通信层 | MQTT / Modbus、ROS2（DDS）、分布式软总线（鸿蒙） | 实训室已有 + 后续引入 |
| 设备层 | 固定传感器与摄像头、PLC 执行器、myAGV（激光雷达 + 车载摄像头） | 实训室已有 + 移动侧新增 |

## 5. 选型与放弃项

| 环节 | 选型 | 理由 | 放弃的替代方案 |
|---|---|---|---|
| 建图导航 | ROS2 + NAV2 | myAGV 原生支持，SLAM 生态成熟，可直接进 Gazebo 仿真 | 自研导航栈 |
| 仿真验证 | Gazebo Harmonic | 无实物先跑任务流，雷达、摄像头模型齐全，ros_gz 桥接 ROS2 | 只做静态 PPT 演示 |
| 统一管理 | OpenHarmony（QEMU） | 分布式软总线统一接入固定与移动设备；具身智能版已集成仿真环境 | 各设备各管一套入口 |
| 推理算力 | 校内本地算力服务器 | 校内已有资源，推理在校内完成，数据不出校 | 全部走云端 API |
| 派单记录 | 大模型智能体 | 自然语言转任务链、自动生成记录，有学术与行业案例 | **大模型直接控制设备** |
| 识别能力 | 复用现有识别 | 本阶段不要求训练模型，成本最低，先把闭环跑通 | 自训新模型 |

## 6. 人机边界

**机器自动完成**：连续监测与阈值告警、生成移动任务、自主导航、到点拍照、识别复核、生成巡检记录草稿、失败重试、低置信度标记。

**人保留的部分**：处置确认（调光、加肥、用药）、阈值与判定口径的校准、导航失败与现场异常的接管、巡检记录内容的最终确认。

**三条强制转人工规则**：

1. 识别置信度低于设定值，不自动出结论，转人工复核；
2. 连续两次导航失败，自动停车并上报；
3. 涉及高风险处置动作，必须人工确认后才执行。

## 7. 演示脚本与四天计划

演示链路（Gazebo + OpenHarmony QEMU）：搭建简化场景（多层架、myAGV 模型、停靠点）→ 注入一条模拟 EC 越限告警 → 智能体生成移动任务 → NAV2 导航到架位拍照 → 识别结果回传、生成记录 → 人工确认界面展示，鸿蒙 QEMU 侧同步显示统一设备管理。

| 天 | 交付 |

| D2 | 闭环流程、接口口径、架构与选型定稿 |

## 10. 场景参数化与配件模块化（1.1.0 追加）

演示页从「画死的 3 个架位」改成「一套参数生成场景」，目的是让同一份页面能对上不同规模的现场，
也方便现场改口径时当场演示。

### 10.1 参数就是场景

配置对象 `CFG` 是唯一的事实来源：

```js
CFG = {rows, cols, layers, plants, sensorPerRack, ledOn, agvCam, cabOn, fertOn, alertRow, alertCol, props[]}
```

`buildWorld()` 按 `CFG` 推导出全部几何：架位坐标 `rackX(c)/rackZ(r)`、层高 `SHELF_Y`、
走道 `aisleZ(r)`、巡检路径 `WP`、告警环位置、控制柜与水肥机站位、相机全景位 `fitCamera(spanX, spanZ)`。
改参数 → 重算 → 重建，旧对象连同几何一起 dispose，避免反复切换后显存泄漏。

几个刻意的取舍：

- **行号从近到远**：第 1 行是最靠近镜头的一排，编号和人的直觉一致；告警默认落在第 1 行，
  这样 AGV 在最近走道上动作，投屏时不会被前排架体挡住。
- **厂房外壳一次铺底**：地面、后墙、竖梃按最大配置（5 列 × 3 行）一次建好，改行列时只重建架体，
  省掉每次重建整栋厂房的开销。
- **吊顶改成边梁**：整块吊顶在 5 列场景下会挡俯视镜头（相机抬到 6.3 米以上就只看得到顶板），
  改成两侧边梁加后侧一条，既有纵深暗示又不挡视线。
- **相机自动退位**：`R = spanX * 0.78 + 11`、俯角 28°、轻微偏航，保证 15 个架位整体入画，
  同时 AGV 停在走道起点时也在画面里。

### 10.2 配件走「类型库 ＋ 实例」

```js
PROP_TYPES = {
  beacon:   {label: '声光报警器',   make() {...}},
  charger:  {label: '充电桩',       make() {...}},
  camera:   {label: '云台摄像头',   make() {...}},
  tank:     {label: '储液罐',       make() {...}},
  bench:    {label: '操作台',       make() {...}},
  conveyor: {label: '输送线',       make() {...}},
  bed:      {label: '育苗苗床',     make() {...}},
  pack:     {label: '分拣包装台',   make() {...}},
  fan:      {label: '环流风机',     make() {...}},
  co2:      {label: 'CO₂ 补给',     make() {...}},
}
```

实例只存 `{type, x, z, rot}`，渲染时遍历实例、按类型调工厂函数。加一类配件＝加一个工厂函数，
编辑面板的按钮由 `Object.entries(PROP_TYPES)` 自动生成，不用改 UI 代码；删配件＝删数组里的一条。
放置交互是「选中类型 → 点地面 → 射线求交落位」，Esc 取消。

列表里的三个操作都只改实例、不碰几何：**旋转**每次 `rot += π/2`，**复制**在 `(x+0.7, z+0.25)`
处再生成一份（错开而不是重叠，避免看着只有一件），**删除**直接 `splice`。三者收尾都是同一条链路
`rebuildProps() → renderPropList() → saveCfg()`，保证 3D 场景、列表、持久化三处永远一致——
工厂函数只管造模型，位置/朝向/数量全部交给实例数据，不让模型自己记状态。

体积上也有取舍：十类配件共用的材质抽到 `PROP_EXTRA_MATS`（叶菜绿、纸箱、金属），
工厂函数里只新建几何；重建时 `disposeTree` 只 dispose geometry、不销毁材质，
避免反复摆放后材质对象无限增长。

### 10.3 场景可以存档、可以带走

`导出配置 JSON` 把 `CFG` 整个序列化落地（阵列参数、四个开关、告警点位、配件实例），
`导入配置 JSON` 反过来读：字段按白名单逐个校验，行列层夹到 1–3 / 1–6 / 2–5，
配件按 `PROP_TYPES` 白名单过滤，未知类型与非法坐标一律丢弃。写坏的文件不会把场景搞崩，
只会少几个配件——**导入是「容错重放」，不是「照单全收」**。

配套三个布局模板（标准苗床线 3×5 / 小试单排 1×3 / 密集育苗 3×6）只覆盖阵列参数，不动配件：
换产线形态时，桌台上已经摆好的设备没必要跟着消失。

### 10.4 本地运行程序

在线版是 GitHub Pages；离线交付用一个 zip：`index.html` ＋ `启动演示.bat` ＋ `使用说明.txt`。
`index.html` 已把 three.js 内嵌成 `globalThis.__THREE`，页面零外部请求，所以本地端不需要 Node、
也不需要本地服务器，bat 只做两件事：

1. 有 Edge 就 `start msedge --app="file:///…/index.html" --window-size=1600,900`，
   以应用窗口打开、没有标签栏与地址栏，看起来就是个独立程序；
2. 没有 Edge 就退回 `start "" index.html`，交给系统默认浏览器。

bat 用 UTF-8 存、首行 `chcp 65001`，换行是 CRLF——cmd 按行解析，
LF 换行在部分系统上会把括号块读错，这类细节不值得在演示当天踩。

没有做成独立 exe（Electron / PyInstaller）：一是体积与启动时间都远大于一个 1.3 MB 的单文件页面，
二是这类演示的信任成本在于「能双击打开」，打包成 exe 反而会被杀软拦、被怀疑。
zip ＋ 系统浏览器 ＋ 应用窗口是这里阻力最小的路径。
